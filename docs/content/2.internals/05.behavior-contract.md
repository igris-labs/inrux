Inrux owns the expected component behavior. An engine's default behavior is useful only when it meets that contract. This is the architectural decision; complete implementation and cross-engine conformance are still pending.

## Core and adapter ownership

| Responsibility | Owner | Example |
| --- | --- | --- |
| Interaction rules | Inrux Core contract and shared policy | Focus order, keyboard activation, disabled controls and modal containment |
| Accessible meaning | Inrux contract | Names, roles, states, relationships and background exclusion while a modal is open |
| Engine translation | Adapter | Map native input to the contract and publish semantics through the engine's accessibility bridge |
| OS integration | Backend and platform | IME preedit/candidate integration, clipboard transport and native event delivery |
| Text and scrolling | Selected service under Inrux rules | Shared text geometry, system scroll direction and nested-scroll boundaries |

If native tab cycling disagrees with Inrux focus order, the adapter must suppress that cycling and use the shared behavior. One owner handles each action: Core and the backend must not both advance focus or activate the same button.

Core ownership does not require moving native objects into `inrux-core`. Existing shared policy modules live in `inrux-adapter`; native types remain in the engine bindings. Module placement can evolve as the contracts become operational.

## Modal and editing rules

The target modal contract includes initial focus, forward and reverse traversal within the active modal, and focus restoration to a valid trigger or documented fallback on close. Escape closes only a dismissible modal. Background content must not receive pointer, keyboard or accessibility focus through a blocking modal.

The backend still handles platform IME integration. Inrux must prevent Enter from submitting a form during composition and define commit/cancel behavior when an editor resets or unmounts. Testing plain Unicode input does not prove OS composition works.

The current shared Parley/Swash provider owns application glyph geometry and rasterization. Shared scrolling policy owns nested routing and boundaries. Native providers, including scroll inertia, may replace a service when they preserve its contract. Adapters must consume OS-normalized direction once and keep one layout authority per subtree.

## Planned conformance suite

The next shared fixture is a small form and modal, exercised through each adapter's actual input path. A private driver will expose focused logical node IDs, committed text, composition state, scroll offsets and normalized semantic trees. The same scenarios will check:

- Tab and Shift+Tab order, disabled/hidden controls, modal trapping and focus restoration.
- Preedit, commit/cancel, selection replacement and Enter during composition.
- Nested scrolling, remainder propagation and modal scroll boundaries.
- Accessible labels, roles, states, relationships and blocked background content.

A missing feature is an unsupported case, not a passing test. Dialog currently works only in egui; portable modal support is a prerequisite for running that fixture on the other engines.

Headless tests can check routing and semantic output. Real-window tests must also cover OS IME candidates, screen readers, platform shortcuts and system scrolling on each claimed platform. We will record these evidence categories separately. Matching screenshots and passing synthetic events do not establish complete parity.

## Development priority

The current priority is to dogfood one useful application with one primary engine and strengthen these contracts before expanding the component catalogue. The other adapters remain in the build and test matrix. See [current limits](/getting-started/status) and [the architecture](/internals/architecture).
